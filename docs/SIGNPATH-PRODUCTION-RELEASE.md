# Production signing and release runbook

Status: eligibility was confirmed, but production certificate issuance and this release policy have not been confirmed. The workflow is preparation, not proof that production signing works. Ordinary master and PR builds remain unsigned and do not request production signing. Pushing a tag now starts the signing release path rather than publishing unsigned packages; it will fail closed until configured.

## Before enabling

1. Ask SignPath to complete its review and confirm production certificate availability, the exact `release-signing` policy slug, the existing default raw single-PE artifact configuration, trusted GitHub origin and approval rules for this workflow. Do not enable if the actual slug or configuration differs; update the workflow and seek review first. The policy must require SignPath UI approval and restrict submissions to this repository, trusted workflow and authorized release origins. Confirm that SignPath accepts the workflow and hosted runners.
2. In GitHub Settings > Environments create `signpath-production`, restrict eligible deployment tags to authorized release tags and require designated reviewers, prevent self-approval if available. Verify these controls are actually supported and enforced for this repository and plan. Protect master and release tags from unauthorized creation/movement/deletion, including bypass rights; a workflow on an old tag can contain old release logic. Review other workflows and token permissions for alternate publishing or signing paths. Restrict who can edit workflows, environments, secrets and tags. Repository rulesets should be configured and verified independently; the workflow cannot prove these protections.
3. Create a separate SignPath CI identity/token with submit permission for the production policy only; put it **only** in the environment secret `SIGNPATH_PRODUCTION_API_TOKEN`, not a repository or organization secret. Restrict the existing test CI token to test-signing only. Confirm production approvers and MFA in SignPath. Never reuse the test token for production.
4. After verifying the actual production signing certificate out of band, set environment variable `SIGNPATH_PRODUCTION_CERT_SHA256` to its uppercase 64-character SHA-256 certificate fingerprint (not file digest or SHA-1 thumbprint). Set environment variable `SIGNPATH_PRODUCTION_ENABLED` to `true` only after the above controls are working. Update fingerprint deliberately on certificate renewal. Verify the project default artifact configuration signs exactly the native PE.

## Release and recovery

Push an authorized version tag on reviewed master history. The normal build and tests run first. A reviewer approves the GitHub environment, after which a production request is sent to SignPath. Open SignPath, verify request origin, commit, artifact and policy, and approve in the SignPath UI. GitHub environment approval does not replace SignPath approval. The action waits up to four hours; denial, failure or timeout stops publication. Check SignPath's request list and the Actions log for its status and ID; do not approve a stale request blindly. On timeout or cancellation check whether the request is still active, cancel it if necessary, then start a fresh workflow_dispatch run on the same protected tag to submit a new request and approve that request. Do not rerun the signing job: the raw artifact filename can collide with an artifact from the earlier attempt. A new run can create a second request. SignPath pipeline policies may restrict reruns; if so start a new authorized release run as agreed with SignPath. Artifact retention is 14 days.

The signed raw installer is checked for embedded cryptographic integrity, Windows trust and the pinned certificate fingerprint, then copied to the native alias; the manual ZIP is unsigned. The script excludes the Python, Inno and MSI installers until their artifact configurations and signing have been separately reviewed. SHA256SUMS is generated after signing. Only these assets are uploaded, initially to a draft release, then published. The Windows trust check depends on the runner's trust store and network/revocation state and can fail closed.

If publication fails, inspect the tag, run, signed artifact, checksums and any existing draft. Rerun only failed jobs when the signed artifact is still available. A release that already exists is never overwritten: if a draft was partially created, inspect it and either complete it manually with the verified artifact set, or delete the draft and rerun the failed publication job. Do not delete or overwrite a published release without a separate decision. If the tag moved or artifacts expired, investigate and start a new authorized release; never publish an unsigned fallback. Do not put production credentials in PRs.
